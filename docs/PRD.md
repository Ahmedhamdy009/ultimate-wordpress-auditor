# Ultimate WordPress & Website Auditor

## Product Requirements Document (PRD) --- الإصدار 1.0

**الحالة:** مسودة تأسيسية قابلة للتطوير\
**المنصة المستهدفة:** Windows Desktop / Local-first\
**النطاق:** فحص مواقع الويب وWordPress وElementor وWooCommerce\
**مبدأ أساسي:** الفحص للقراءة والتحليل افتراضيًا؛ لا تُجرى تغييرات أو
إصلاحات تلقائية على الموقع دون موافقة صريحة.

------------------------------------------------------------------------

# 1. الملخص التنفيذي

يهدف المشروع إلى بناء أداة محلية متكاملة تساعد مطوري WordPress وأصحاب
المواقع على إجراء مراجعة تقنية وأمنية شاملة للمواقع، ثم تجميع النتائج في
تقرير مفهوم وقابل للتنفيذ.

تتكون المنظومة من:

1.  **Desktop Dashboard:** واجهة لإدارة المواقع والفحوصات والنتائج
    والتقارير.
2.  **Scanning Engine:** محرك الاختبارات الخارجية واختبارات المتصفح
    والأداء وSEO وإمكانية الوصول.
3.  **WordPress Companion Plugin:** إضافة اختيارية وآمنة لجمع معلومات
    داخلية لا يمكن الوصول إليها من خارج الموقع.
4.  **Reporting & Remediation Engine:** محرك لتفسير النتائج وتصنيف
    المخاطر واقتراح خطوات الإصلاح والتحقق منها بإعادة الاختبار.

لا تعد الأداة بديلًا عن مراجعة خبير أمني، ولا يمكنها إثبات خلو الموقع من
جميع الثغرات. يجب أن تعرض حدود كل اختبار، ومصدر النتيجة، ومستوى الثقة،
واحتمال وجود نتائج إيجابية كاذبة.

# 2. الأهداف

-   تقليل وقت الفحص اليدوي قبل تسليم مواقع العملاء.
-   اكتشاف أخطاء الموقع وووردبريس والإضافات والقوالب والإعدادات.
-   اكتشاف الثغرات المعروفة ومؤشرات الاختراق والتهيئة الأمنية الضعيفة.
-   اختبار الصفحات على أحجام شاشات ومتصفحات مختلفة.
-   اختبار الأداء وSEO وإمكانية الوصول.
-   تقديم إرشادات إصلاح عملية ومحددة لكل مشكلة.
-   إعادة الاختبار بعد الإصلاح ومقارنة النتائج السابقة بالحالية.
-   دعم المواقع المحلية عبر LocalWP والمواقع المنشورة التي يملك المستخدم
    تصريحًا بفحصها.

# 3. المستخدمون المستهدفون

-   مطورو WordPress وElementor.
-   مطورو WooCommerce.
-   أصحاب المواقع.
-   فرق ضمان الجودة QA.
-   مقدمو خدمات صيانة المواقع والتدقيق قبل التسليم.

# 4. مبادئ التصميم والأمان

1.  **Read-only by default:** لا تعديل أو حذف أو تحديث تلقائي أثناء
    الفحص.
2.  **Authorization first:** لا فحص نشط إلا لموقع يملكه المستخدم أو لديه
    تصريح مكتوب بفحصه.
3.  **Least privilege:** الإضافة تجمع أقل قدر من البيانات وبأقل صلاحيات
    ممكنة.
4.  **No secrets collection:** لا تجمع كلمات مرور المستخدمين أو مفاتيح
    API أو بيانات الدفع.
5.  **Local-first:** تحفظ التقارير محليًا افتراضيًا، مع إمكانية التصدير.
6.  **Evidence-based findings:** كل نتيجة يجب أن تتضمن دليلًا قابلًا
    للمراجعة.
7.  **Safe testing:** الاختبارات التخريبية أو التي قد تؤثر في البيانات
    أو الخدمة غير مفعّلة.
8.  **Human approval:** أي إصلاح مستقبلي يحتاج موافقة صريحة ونسخة
    احتياطية وخطة تراجع.

# 5. نطاق المنتج

## 5.1 النطاق الأساسي (MVP)

-   إدارة المشاريع والمواقع.
-   فحص خارجي للصفحات والروابط.
-   اختبارات المتصفح والـ responsive.
-   Lighthouse للأداء وSEO وBest Practices.
-   axe-core لفحوص إمكانية الوصول.
-   فحص معلومات WordPress الداخلية عبر الإضافة.
-   مراجعة إصدارات WordPress والإضافات والقوالب والثغرات المعروفة.
-   فحص إعدادات المستخدمين والصلاحيات والتحديثات.
-   تقارير HTML وJSON، ثم PDF في إصدار لاحق.
-   إدارة النتائج وإعادة الاختبار.

## 5.2 النطاق المتقدم

-   فحوص OWASP ZAP النشطة ضمن إعدادات آمنة ومصرح بها.
-   فحوص سلامة ملفات WordPress.
-   فحص مؤشرات الملفات المشبوهة والبرمجيات الضارة.
-   فحص WooCommerce وسيناريوهات المتجر التجريبية.
-   اختبار البريد والتكاملات وواجهات API.
-   جدولة الفحوصات ومقارنة التغيرات.
-   اختبارات استعادة النسخ الاحتياطية في بيئة منفصلة.

## 5.3 ما لا يدخل في النطاق

-   اختراق مواقع الغير أو تجاوز صلاحيات الوصول.
-   استغلال الثغرات لإثبات السيطرة على النظام.
-   حذف ملفات أو حسابات أو إضافات.
-   تنفيذ معاملات مالية حقيقية.
-   ضمان اكتشاف جميع البرمجيات الخبيثة أو جميع الثغرات.
-   إجراء تغييرات إنتاجية تلقائية دون موافقة.

# 6. وحدات الفحص التفصيلية

## 6.1 Website & Frontend Audit

-   التحقق من إتاحة الموقع والصفحات.
-   أكواد HTTP والتحويلات وسلاسل التحويل.
-   الروابط الداخلية والخارجية المعطوبة.
-   الصور والملفات المفقودة.
-   عناوين الصفحات وبيانات الاستجابة.
-   أخطاء JavaScript في Console.
-   فشل تحميل CSS وJavaScript والخطوط والصور.
-   اختبار القوائم والأزرار والتنقل.
-   اختبار النماذج في بيئة آمنة وببيانات اختبار.
-   التقاط لقطات شاشة للصفحات.
-   كشف العناصر الخارجة عن حدود الشاشة والتمرير الأفقي.

**قيد:** لا يمكن التأكد من صحة المعنى أو جودة التصميم الجمالية آليًا
بصورة موثوقة بالكامل.

## 6.2 Responsive & Browser Compatibility

-   أحجام Desktop وTablet وMobile.
-   Portrait وLandscape.
-   Chromium، مع دعم متصفحات إضافية حسب بيئة التشغيل.
-   اكتشاف التداخل والقص والتمرير الأفقي.
-   فحص الصور والخطوط والقوائم والنوافذ المنبثقة.
-   مقارنة لقطات الشاشة بين الإصدارات.

## 6.3 WordPress Core Audit

-   إصدار WordPress وحالة التحديث.
-   سلامة ملفات Core عبر آليات التحقق الرسمية المناسبة.
-   إعدادات Debug وعدم تسريب الأخطاء.
-   REST API وسلوك الوصول المتوقع.
-   WP-Cron والمهام المجدولة.
-   Permalinks.
-   حدود الذاكرة والرفع وإعدادات PHP المتاحة.
-   إعدادات التحديث التلقائي.
-   إعدادات القراءة والفهرسة.
-   التحقق من وجود ملفات تثبيت أو ملفات افتراضية غير لازمة عند إمكان
    ذلك.

## 6.4 Plugins Audit

-   قائمة الإضافات النشطة وغير النشطة.
-   الإصدارات والإصدارات المتاحة.
-   حالة الصيانة والتوافق عند توفر بيانات موثوقة.
-   مطابقة الإصدارات مع قواعد بيانات الثغرات المعروفة.
-   اكتشاف الإضافات المكررة أو غير المستخدمة.
-   فحص سلامة الملفات حيث تتوفر بصمة موثوقة.
-   إظهار تاريخ مصدر بيانات الثغرات وتاريخ آخر تحديث له.

**تنبيه:** لا يُستنتج وجود ثغرة من مجرد قدم الإضافة؛ يجب مطابقة الإصدار
المتأثر وشروط الثغرة.

## 6.5 Themes Audit

-   القالب النشط والقوالب المثبتة.
-   الإصدارات والتحديثات.
-   القوالب غير المستخدمة.
-   سلامة الملفات عند توفر مصدر موثوق للمقارنة.
-   Child Theme ومؤشرات التعديلات.
-   الثغرات المعروفة.

## 6.6 Elementor Audit

-   إصدارات Elementor وElementor Pro عند وجوده.
-   حالة التوافق والإصدارات.
-   معلومات القوالب المحفوظة وTheme Builder المتاحة.
-   مؤشرات فشل تحميل الموارد.
-   أخطاء JavaScript المرتبطة بالواجهة.
-   فحص صفحات مختارة على مقاسات متعددة.
-   اكتشاف تجاوز العرض والتداخل ومشكلات الظهور.
-   فحص النماذج والنوافذ المنبثقة في بيئة اختبار.

**قيد:** لا تستطيع الأداة الحكم الكامل على جودة التصميم أو صحة كل إعداد
بصري داخل المحرر دون اختبارات مخصصة ومراجعة بشرية.

## 6.7 Security Configuration Audit

-   HTTPS وشهادة TLS.
-   HTTP Security Headers.
-   إعدادات Cookies وخصائصها عند إمكان التحقق.
-   صلاحيات الملفات والمجلدات.
-   إعدادات wp-config.php دون عرض الأسرار.
-   تعطيل أو تقييد تحرير الملفات من لوحة التحكم عند ملاءمة سياسة الموقع.
-   إعدادات XML-RPC وREST API وفق الحاجة الفعلية.
-   حماية صفحة الدخول ومؤشرات محاولات التخمين.
-   أدوار المستخدمين والصلاحيات الزائدة.
-   حسابات المديرين غير المتوقعة.
-   إعدادات النسخ الاحتياطي.
-   كشف الملفات الحساسة المكشوفة خارجيًا.

## 6.8 Vulnerability Assessment

-   مطابقة WordPress Core والإضافات والقوالب مع قواعد بيانات الثغرات.
-   فحص خارجي سلبي أولًا.
-   فحص نشط محدود ومصرح به باستخدام OWASP ZAP أو أدوات مناسبة.
-   اختبارات آمنة للتحقق من إعدادات التطبيق.
-   تصنيف النتائج وفق CVSS عند توفر درجة موثوقة، مع توضيح أن الدرجة لا
    تمثل وحدها خطورة السياق.
-   ربط كل نتيجة بالمرجع والإصدار المتأثر وشروط التأثر.
-   منع الاختبارات التي تغير البيانات أو تسبب تعطيل الخدمة.

أنواع المخاطر التي يمكن تقييمها بحسب الاختبار والأدلة: - SQL Injection
indicators. - Cross-Site Scripting indicators. - CSRF protections. -
Broken Access Control indicators. - Authentication and session
weaknesses. - File upload configuration weaknesses. - Path traversal
indicators. - Information disclosure. - Security misconfiguration. -
SSRF indicators.

**قيد أساسي:** ظهور مؤشر لا يثبت وجود ثغرة قابلة للاستغلال. يجب تأكيد
النتائج يدويًا أو باختبار آمن مناسب، وعدم عرضها كحقيقة مؤكدة دون دليل
كافٍ.

## 6.9 Malware & File Integrity

-   مقارنة ملفات WordPress الأساسية بمصادر موثوقة.
-   رصد الملفات الجديدة أو المعدلة خارج التغييرات المعروفة.
-   فحص مؤشرات الشيفرات والملفات المشبوهة.
-   فحص الملفات باستخدام محرك مضاد للبرمجيات الخبيثة عند توفره.
-   تسجيل المسار والبصمة والتوقيت وسبب الاشتباه.
-   عدم حذف أو عزل الملفات تلقائيًا.

**قيد:** الملف المعدل ليس بالضرورة خبيثًا؛ قد يكون تعديلًا مشروعًا أو جزءًا
من إضافة أو قالب.

## 6.10 Users & Permissions Audit

-   قائمة المستخدمين وأدوارهم.
-   الحسابات ذات الصلاحيات المرتفعة.
-   حسابات غير مستخدمة أو غير متوقعة وفق معايير يحددها مالك الموقع.
-   مراجعة توزيع الصلاحيات.
-   كشف إعدادات تسجيل الدخول الضعيفة التي يمكن التحقق منها دون جمع كلمات
    المرور.
-   عدم محاولة تخمين كلمات المرور أو اختبارها.

## 6.11 Database Audit

-   الاتصال وحالة الجداول.
-   حجم قاعدة البيانات.
-   الجداول الكبيرة.
-   خيارات autoload المرتفعة.
-   مؤشرات البيانات اليتيمة.
-   Transients والبيانات المؤقتة.
-   أخطاء الاتصال.
-   إعدادات الوصول الخارجي التي يمكن التحقق منها.
-   مؤشرات الأداء دون تنفيذ تغييرات تلقائية.

## 6.12 Server & Infrastructure Audit

-   إصدار PHP والتوافق.
-   إعدادات PHP المهمة وحدود الموارد.
-   خادم الويب والمعلومات المكشوفة.
-   DNS وSSL/TLS.
-   HTTP Headers.
-   المنافذ المكشوفة ضمن نطاق مصرح به.
-   إعدادات التخزين المؤقت والضغط.
-   مؤشرات كشف ملفات السجل والنسخ الاحتياطية.
-   معلومات الاستضافة المتاحة من داخل WordPress.

## 6.13 Performance Audit

-   Lighthouse Performance.
-   Core Web Vitals: LCP وINP وCLS.
-   TTFB ووقت التحميل.
-   حجم الصفحة وعدد الطلبات.
-   الصور الكبيرة والتنسيقات الحديثة.
-   Lazy Loading.
-   CSS وJavaScript blocking.
-   Cache وCompression.
-   الخطوط وموارد الطرف الثالث.
-   قياسات Mobile وDesktop.

**قيد:** النتائج تتأثر بموقع الاختبار والشبكة والخادم ووقت القياس؛ لذلك
يجب حفظ ظروف القياس وعدم التعامل مع الدرجة كقيمة مطلقة.

## 6.14 SEO Audit

-   Titles وMeta Descriptions.
-   H1/H2.
-   Canonical.
-   Sitemap وRobots.txt.
-   Indexability وMeta Robots.
-   Status Codes وRedirects.
-   Duplicate Titles وDescriptions.
-   Image Alt.
-   Structured Data.
-   Open Graph وSocial Metadata.
-   Internal Linking.
-   صفحات 404.
-   Mobile checks.

## 6.15 Accessibility Audit

-   axe-core وLighthouse وWAVE عند الحاجة.
-   التباين اللوني.
-   التسميات البديلة.
-   أسماء الأزرار والروابط.
-   بنية العناوين.
-   Labels للنماذج.
-   التنقل بلوحة المفاتيح.
-   مؤشرات التركيز.
-   ARIA misuse.
-   فحص تلقائي مع توضيح أن المراجعة اليدوية بقارئ شاشة ولوحة مفاتيح
    لازمة لبعض المعايير.

## 6.16 WooCommerce Audit

يعمل فقط عند اكتشاف WooCommerce أو تفعيله للمشروع: - إصدارات WooCommerce
والتوافق. - إعدادات العملة والضرائب والشحن. - صفحات المتجر والسلة والدفع
والحساب. - المنتجات البسيطة والمتغيرة والخصائص والمخزون. - الكوبونات. -
حالات الطلبات. - رسائل البريد. - بوابات الدفع في وضع Sandbox. - Webhooks
والتكاملات. - سيناريوهات الطلب التجريبي دون تحصيل أموال حقيقية.

## 6.17 Email & Integrations

-   إعدادات SMTP المتاحة.
-   اختبار إرسال إلى صندوق اختبار يحدده المستخدم.
-   نماذج الاتصال.
-   Webhooks.
-   REST API integrations.
-   Google Sheets وWhatsApp وTelegram وغيرها حسب التكامل.
-   تسجيل فشل الطلبات وأكواد الاستجابة.
-   عدم تسجيل مفاتيح API أو محتويات حساسة.

## 6.18 Backup & Recovery

-   وجود نسخ احتياطية وحداثتها.
-   اكتمال الملفات وقاعدة البيانات.
-   مكان التخزين وصلاحيات الوصول.
-   فحص سلامة ملفات النسخة.
-   تجربة استعادة على بيئة Staging منفصلة.
-   قياس زمن الاستعادة ومدى اكتمال الموقع.
-   عدم إجراء استعادة على موقع الإنتاج تلقائيًا.

# 7. WordPress Companion Plugin

## 7.1 المسؤوليات

-   إنشاء اتصال موثق وآمن مع التطبيق المحلي.
-   جمع بيانات WordPress الضرورية للفحص الداخلي.
-   عرض معلومات Core والإضافات والقوالب والإصدارات.
-   جمع بيانات الأدوار والصلاحيات دون كلمات مرور.
-   تشغيل فحوص قراءة فقط.
-   توفير فحص سلامة الملفات عند توافر آلية موثوقة.
-   جمع معلومات PHP والبيئة التي يسمح WordPress بعرضها.
-   إرسال النتائج الموقعة أو المحمية إلى التطبيق.
-   تسجيل عمليات الفحص وتاريخها.
-   السماح بإلغاء الربط وإبطال رموز الاتصال.

## 7.2 متطلبات الأمان

-   استخدام HTTPS للمواقع المنشورة.
-   مصادقة قوية بين التطبيق والإضافة.
-   رموز قصيرة العمر وقابلة للإبطال.
-   Nonces والتحقق من الصلاحيات.
-   حماية من replay attacks عند تصميم بروتوكول الاتصال.
-   تحديد معدل الطلبات.
-   التحقق من المدخلات.
-   عدم كشف REST endpoints للعامة.
-   عدم تخزين أسرار الاستضافة أو الدفع.
-   عدم تنفيذ أوامر shell مرسلة من التطبيق.
-   عدم تنفيذ SQL اعتباطي.
-   عدم توفير وظائف إصلاح في الإصدار الأول.
-   سجل تدقيق واضح.

## 7.3 الصلاحيات

يجب أن تستخدم الإضافة أقل صلاحية مناسبة لكل عملية. لا تُطلب صلاحية
Administrator لمجرد جمع معلومات عامة إذا أمكن تنفيذ ذلك بصلاحية أقل.
العمليات الحساسة تتطلب تحققًا إضافيًا وموافقة مالك الموقع.

# 8. بنية النظام التقنية

## 8.1 Desktop Application

-   واجهة مقترحة: React.
-   بيئة تشغيل سطح المكتب: Electron أو بديل مناسب بعد تقييم المتطلبات.
-   لغة المحرك: Node.js وTypeScript.
-   قاعدة بيانات محلية: SQLite.
-   تخزين التقارير واللقطات محليًا.

## 8.2 Scanning Engine

-   Playwright لاختبارات المتصفح.
-   Lighthouse لاختبارات الأداء.
-   axe-core لإمكانية الوصول.
-   Screaming Frog أو زاحف داخلي بديل لفحص الروابط والصفحات.
-   WP-CLI للفحوص المحلية المصرح بها.
-   WPScan لمطابقة ثغرات WordPress المعروفة.
-   OWASP ZAP للاختبارات الأمنية المصرح بها.
-   SSL Labs أو فحوص TLS المناسبة.
-   Nmap لفحص المنافذ ضمن نطاق مصرح به فقط.
-   ClamAV أو محرك مناسب لفحص الملفات.

يجب التحقق من تراخيص الأدوات وشروط الاستخدام وإصداراتها قبل دمجها أو
توزيع البرنامج.

## 8.3 Data Flow

1.  المستخدم ينشئ مشروعًا ويضيف عنوان الموقع.
2.  النظام يتحقق من الملكية أو التصريح ونطاق الفحص.
3.  يبدأ الفحص الخارجي ضمن حدود محددة.
4.  إذا كانت إضافة Companion مثبتة، يطلب النظام الفحوص الداخلية المسموح
    بها.
5.  تتحقق الإضافة من هوية التطبيق وصلاحيات الطلب.
6.  ترسل الإضافة الحد الأدنى من نتائج الفحص.
7.  يوحد المحرك النتائج ويزيل التكرار.
8.  يصنف المخاطر ويضيف الأدلة والمراجع.
9.  ينشئ التقرير.
10. يراجع المستخدم النتائج ويصلحها خارج النظام.
11. ينفذ Retest للمشكلات المختارة ويقارن النتائج.

# 15. معايير القبول (Acceptance Criteria)

لا يعتبر الإصدار جاهزًا إلا عند تحقق الآتي:

-   يستطيع المستخدم إنشاء مشروع وإضافة موقع.
-   يرفض النظام تجاوز نطاق الفحص المحدد.
-   يستطيع إجراء فحص خارجي دون تثبيت الإضافة.
-   يستطيع ربط Companion Plugin بطريقة موثقة.
-   لا تظهر الأسرار في السجلات أو التقارير.
-   لا تنفذ الإضافة تغييرات على الموقع في وضع التدقيق.
-   كل نتيجة تتضمن دليلًا ومصدرًا أو توضح سبب غياب المصدر.
-   تُعرض النتائج المحتملة باعتبارها محتملة لا مؤكدة.
-   يمكن تصدير تقرير قابل للقراءة.
-   يمكن إعادة اختبار مشكلة ومقارنة النتيجة.
-   يمكن إيقاف الفحص وإبطال الربط.
-   تُختبر الأداة على موقع تجريبي يحتوي عمدًا على حالات اختبار معروفة.
-   تُقاس النتائج الإيجابية الكاذبة والسلبية الكاذبة قدر الإمكان.

# 18. المخاطر والقيود

-   قواعد بيانات الثغرات قد تتأخر عن الإصدارات الجديدة.
-   بعض الاستضافات تمنع أدوات الفحص أو تحد من صلاحياتها.
-   الفحص النشط قد يسبب ضغطًا؛ لذلك يحتاج حدود سرعة ومواعيد مناسبة.
-   لا يمكن فحص كل سلوك تجاري أو بصري آليًا.
-   قد تنتج أدوات الأمن إنذارات كاذبة.
-   اختلاف إعدادات التخزين المؤقت والشبكة يؤثر على قياسات الأداء.
-   بعض وظائف Elementor وWooCommerce تحتاج بيانات اختبار وحسابات
    تجريبية.
-   قد تتطلب بعض الأدوات اشتراكًا أو تراخيص خاصة.

# 19. قرارات لم تُحسم بعد

هذه القرارات تُحسم قبل التنفيذ النهائي: - Electron أم تطبيق محلي بواجهة
Web؟ - هل يحتاج البرنامج إلى العمل دون إنترنت بالكامل؟ - هل سيُدعم فحص
مواقع متعددة في وقت واحد؟ - ما حدود الفحص الافتراضية وعدد الصفحات؟ - هل
ستُضاف جدولة تلقائية في الإصدار الأول أم لاحقًا؟ - ما الأدوات التي ستُدمج
مباشرة وما الأدوات التي ستعمل كتكاملات خارجية؟ - ما الحد الأدنى لإصدارات
Windows وPHP وWordPress المدعومة؟

# 20. تعريف النجاح النهائي

يُعد المشروع ناجحًا عندما يستطيع المستخدم، لموقع يملكه أو لديه تصريح
بفحصه:

1.  إضافة الموقع وربطه اختياريًا بإضافة Companion.
2.  تشغيل Quick Scan أو Full Audit أو Deep Security Audit.
3.  الحصول على نتائج موثقة من الموقع وWordPress والواجهة والخادم ضمن
    حدود الصلاحيات.
4.  معرفة المشكلات ومواقعها وأولوياتها.
5.  اتباع تعليمات إصلاح واضحة.
6.  إعادة الاختبار والتحقق من الإصلاح.
7.  حفظ تقرير ومقارنته بفحوصات سابقة.

**الهدف النهائي:** تحويل فحص الموقع قبل التسليم أو أثناء الصيانة من
عملية يدوية متفرقة إلى سير عمل منظم، قابل للتكرار، موثق، وآمن.
